# OpenFlux — автоматическое управление нодой

Этот набор скриптов ставит [OpenFlux](https://github.com/p1neappleXpress/OpenFlux) на сервер (Ubuntu/Debian) и даёт одну команду `openflux-ctl` для всего: добавить транспорт, перезапустить, посмотреть логи, включить автообновление с GitHub.

Инструкция написана в расчёте на то, что ты впервые видишь Linux-консоль. Каждую команду можно просто скопировать и вставить.

## Что тут есть

| Файл | Что делает |
|---|---|
| `setup.sh` | Ставится один раз. Устанавливает Go, скачивает код OpenFlux, кладёт команду `openflux-ctl`, включает сетевое правило и защиту от переполнения диска логами. |
| `openflux-ctl` | Команда на каждый день. Ей ты добавляешь/удаляешь ноды, смотришь логи, включаешь автообновление. |
| `openflux-deploy` | Работает "за кулисами": скачивает новый код и перезапускает ноды. Вызывается либо автоматически (по расписанию), либо командой `openflux-ctl deploy`. |

Тебе почти всегда нужен только **`openflux-ctl`**. Два других файла трогать не придётся.

## Установка с нуля

Тебе нужен пустой сервер на Ubuntu или Debian, к которому есть доступ по SSH под пользователем `root` (или через `sudo`).

**1. Зайди на сервер по SSH.**

**2. Скачай файлы прямо из репозитория** — двумя способами, любой подойдёт.

Способ А, через `git clone` (проще, сразу все файлы разом):

```bash
cd /root
git clone https://github.com/Kr1spy2023/openflux-guide.git
cd openflux-guide
```

Способ Б, через `curl`, по одному файлу (если `git` ещё не поставлен и ставить его не хочется):

```bash
mkdir -p /root/openflux-install && cd /root/openflux-install
curl -O https://raw.githubusercontent.com/Kr1spy2023/openflux-guide/main/setup.sh
curl -O https://raw.githubusercontent.com/Kr1spy2023/openflux-guide/main/openflux-ctl
curl -O https://raw.githubusercontent.com/Kr1spy2023/openflux-guide/main/openflux-deploy
```

Проверь, что файлы скачались правильно (не страница с ошибкой):

```bash
head -3 setup.sh
```

Должно быть:
```
#!/bin/bash
# setup.sh — ставит OpenFlux с нуля...
```

Если видишь что-то вроде `404: Not Found` — значит файла по этому пути в репозитории нет (проверь, что он реально загружен в ветку `main` в корень репозитория), либо ветка называется иначе (`master`) — тогда замени `main` на `master` в ссылках выше.

Если ни `git`, ни доступа к репозиторию нет — можно создать файлы и вручную:

```bash
mkdir -p /root/openflux-install && cd /root/openflux-install
nano setup.sh
```

Вставь содержимое файла (скопировав его откуда угодно, где он у тебя есть), сохрани: `Ctrl+O`, `Enter`, `Ctrl+X`. Повтори для `openflux-ctl` и `openflux-deploy`.

**3. Запусти установку:**

```bash
cd /root/openflux-guide   # если качал через git clone
# или
cd /root/openflux-install # если качал через curl
sudo bash setup.sh
```

Скрипт сам:
- поставит Go (через `snap`) и нужные пакеты;
- скачает код OpenFlux с GitHub и соберёт программу;
- создаст ключ шифрования (если его ещё нет) — **сохрани его**, он выведется на экран;
- включит сетевое правило iptables (см. [ниже](#что-делают-эти-два-правила-iptables));
- ограничит системные логи, чтобы диск не забился (как это однажды уже случилось);
- включит автообновление каждые 10 минут.

В конце увидишь:

```
Установка завершена.
Дальше: добавь хотя бы одну ноду...
```

## Первый запуск: добавляем ноду

Формат:

```bash
openflux-ctl add <транспорт> <ссылка>
```

Доступные транспорты: `yandex`, `vyandex`, `boards`, `mailru`, `cupsonline`.

Примеры:

```bash
openflux-ctl add yandex https://disk.yandex.ru/i/XXXXXXXXXXXXXX
openflux-ctl add mailru https://cloud.mail.ru/public/XXXX/XXXXXXXX
openflux-ctl add boards "https://boards.yandex.ru/whiteboard/?hash=XXXXXXXX"
```

Если ссылка содержит символы `&`, `?`, `#` — бери её в кавычки, как в примере с `boards` выше, иначе консоль может обрезать часть ссылки.

По умолчанию нода получает имя транспорта (`yandex`, `mailru`...). Если транспортов одного типа нужно несколько — задай своё имя третьим аргументом:

```bash
openflux-ctl add yandex https://disk.yandex.ru/i/AAAA yandex-work
openflux-ctl add yandex https://disk.yandex.ru/i/BBBB yandex-home
```

Проверь, что нода запустилась:

```bash
openflux-ctl list
```

Ожидаемый результат:

```
ИМЯ              ТРАНСПОРТ    АВТОЗАПУСК  СОСТОЯНИЕ
yandex           yandex       enabled     работает
```

Если написано «ПЕРЕЗАПУСКАЕТСЯ (ошибка!)» или «УПАЛА» — смотри логи:

```bash
openflux-ctl logs yandex
```

## Все команды `openflux-ctl`

Запусти `openflux-ctl help` в любой момент, чтобы увидеть этот список прямо в консоли.

### Управление нодами

| Команда | Что делает |
|---|---|
| `openflux-ctl list` | Показать все ноды и их состояние |
| `openflux-ctl add <транспорт> <ссылка> [имя]` | Добавить новую ноду |
| `openflux-ctl set-url <имя> <новая ссылка>` | Поменять ссылку у существующей ноды (например, старая протухла) |
| `openflux-ctl remove <имя>` | Удалить ноду (спросит подтверждение) |
| `openflux-ctl remove <имя> -y` | Удалить без вопроса |
| `openflux-ctl status <имя>` | Подробный статус конкретной ноды |
| `openflux-ctl logs <имя>` | Последние строки лога |
| `openflux-ctl logs <имя> -f` | Следить за логами в реальном времени (выход — `Ctrl+C`) |

### Запуск/остановка

| Команда | Что делает |
|---|---|
| `openflux-ctl start <имя>` | Запустить ноду |
| `openflux-ctl stop <имя>` | Остановить ноду |
| `openflux-ctl restart <имя>` | Перезапустить ноду |
| `openflux-ctl start all` | То же самое, но для всех нод сразу |
| `openflux-ctl enable <имя>` | Включить автозапуск при перезагрузке сервера |
| `openflux-ctl disable <имя>` | Выключить автозапуск (сама нода не остановится, пока не сделаешь `stop`) |

Если написать команду совсем без имени (`openflux-ctl restart`), она тоже применится ко всем нодам — как `all`.

### Отладка

```bash
openflux-ctl debug yandex on
```

Включает подробный лог (по строке на каждый пакет). Полезно на 1–2 минуты, чтобы понять, в чём проблема. **Не забудь выключить**, иначе за несколько часов может забить весь диск:

```bash
openflux-ctl debug yandex off
```

### Обновления с GitHub

| Команда | Что делает |
|---|---|
| `openflux-ctl deploy` | Прямо сейчас проверить GitHub, и если есть новый код — скачать, собрать, перезапустить ноды |
| `openflux-ctl deploy --force` | То же самое, даже если версия не изменилась (полезно, если что-то пошло не так и хочется пересобрать заново) |
| `openflux-ctl auto on 10` | Включить автопроверку каждые 10 минут (число можно другое, от 1 до 59) |
| `openflux-ctl auto off` | Выключить автопроверку |
| `openflux-ctl auto status` | Посмотреть, включена ли автопроверка, и последние строки её журнала |

### Ключ шифрования

```bash
openflux-ctl key show     # показать текущий ключ
openflux-ctl key new      # создать новый (переподключит все ноды, спросит подтверждение)
```

### Проверка всей системы

```bash
openflux-ctl check
```

Подробнее — [в отдельном разделе ниже](#проверка-здоровья-сервера).

### Полное удаление

```bash
openflux-ctl uninstall            # оставит код и ключ на диске
openflux-ctl uninstall --purge    # удалит вообще всё, включая ключ шифрования
```

## Режим session (несколько транспортов сразу)

Обычная нода (`openflux-ctl add ...`) использует один транспорт. Режим **session** объединяет несколько транспортов в одну ноду с приоритетами — если первый недоступен, используется следующий.

**1. Сначала добавь обычные ноды под каждый транспорт**, как в разделе выше:

```bash
openflux-ctl add boards "https://boards.yandex.ru/whiteboard/?hash=XXXX"
openflux-ctl add vyandex https://disk.yandex.ru/i/AAAA
openflux-ctl add yandex https://disk.yandex.ru/i/BBBB
openflux-ctl add mailru https://cloud.mail.ru/public/CCCC
```

**2. Собери их в session, перечислив имена в порядке приоритета** (первый — самый желаемый):

```bash
openflux-ctl session boards vyandex yandex mailru
```

Если запустить `openflux-ctl session` без имён — он сам возьмёт все существующие одиночные ноды.

**3. Получи ссылку для клиента:**

```bash
openflux-ctl link
```

Эта ссылка содержит ключ шифрования — никому её не пересылай в открытом виде.

**Важно:** если те же самые ссылки одновременно использует и session, и отдельная одиночная нода — они будут мешать друг другу (два узла полезут в один документ). Если создал session — обычно стоит остановить одиночные ноды с тем же transport:

```bash
openflux-ctl stop yandex
openflux-ctl disable yandex
```

Сама нода при этом остаётся в списке (`openflux-ctl list` её покажет), просто не работает — так удобнее, если понадобится вернуть её обратно без пересоздания.

## Автообновление с GitHub

По умолчанию (после `setup.sh`) включена проверка каждые 10 минут. Как это работает:

1. Раз в N минут запускается `openflux-deploy`.
2. Он сравнивает код на сервере с веткой `main` на GitHub.
3. Если есть новый коммит — скачивает, собирает.
4. **Если сборка не удалась** — старый код и все ноды продолжают работать без изменений, ничего не ломается.
5. Если сборка удалась — перезапускает **все включённые** ноды (`openflux-ctl enable`), чтобы они подхватили новый код.

Посмотреть журнал обновлений:

```bash
cat /var/log/openflux-deploy.log
```

Только последние строки:

```bash
tail -20 /var/log/openflux-deploy.log
```

Изменить частоту проверки (например, раз в час — но `auto on` принимает только минуты, для часа поставь 59, это максимум, либо не включай `auto` и обновляй через `crontab -e` вручную более гибким расписанием):

```bash
openflux-ctl auto on 30
```

## Проверка здоровья сервера

```bash
openflux-ctl check
```

Эта команда проверяет всё разом: код актуален ли, все ли ноды работают, есть ли сетевое правило, не забивается ли диск логами, не подвисает ли процессор в ожидании диска (это уже однажды приводило к «зависанию» сервера).

Результат сохраняется в файл и **всегда перезаписывается заново**, так что файл не растёт:

```bash
cat /root/openflux-checklist.txt
```

В конце команда пишет число найденных проблем:

```
Проблем: 0, предупреждений: 1
```

Если `Проблем: 0` — всё в порядке, предупреждения можно изучить не спеша. Если проблем больше нуля — в самом отчёте `[FAIL]` отмечает, что именно не так, и что сделать, чтобы починить.

Гоняй эту команду:
- после установки — убедиться, что всё поднялось;
- после добавления новой ноды;
- если что-то работает не так;
- просто периодически, для профилактики.

## Частые ситуации

### Добавить ещё один транспорт

```bash
openflux-ctl add cupsonline https://cups.online/room/XXXX
```

### У ноды протухла ссылка, нужно заменить

```bash
openflux-ctl set-url yandex https://disk.yandex.ru/i/НОВАЯ_ССЫЛКА
```

### Нода постоянно падает и перезапускается

```bash
openflux-ctl logs имя_ноды
```

Прочитай последнюю ошибку в конце вывода — она обычно прямо объясняет причину (неверная ссылка, авторизация не пройдена, и т.п.).

### Диск почти заполнен

```bash
openflux-ctl check
```

Отчёт скажет, если `syslog` разросся или диск заполнен больше 80%. Быстрая ручная чистка:

```bash
sudo truncate -s 0 /var/log/syslog
sudo journalctl --vacuum-size=100M
```

### Нужно перенести всё на новый сервер

На новом сервере:
1. Повтори [установку](#установка-с-нуля) (`setup.sh`).
2. Скопируй файл `/root/openflux-secrets/encryption-key` со старого сервера (если хочешь сохранить тот же ключ — иначе `setup.sh` создаст новый).
3. Добавь те же ноды заново командами `openflux-ctl add ...` — ссылки нужно ввести вручную, их скрипт не переносит сам.

### Сервер перезагрузился (или упал и поднялся заново)

Ничего делать не надо — все ноды, у которых включён автозапуск (`enabled`), поднимутся сами. Сетевое правило iptables тоже восстановится само. Проверь после перезагрузки:

```bash
openflux-ctl check
```

## Что делают эти два правила iptables

При установке `setup.sh` добавляет такое правило (дважды — для новой и старой версии iptables на некоторых системах):

```bash
iptables -A OUTPUT -p tcp --tcp-flags RST RST -j DROP
```

Простыми словами: сервер перестаёт сам отправлять TCP-пакеты с флагом `RST` (это пакет, которым операционная система обычно резко обрывает соединение). Это нужно транспортам OpenFlux, чтобы работать поверх обычных TCP-сессий, не давая системе Linux случайно разрывать эти соединения снизу.

Правило хранится не в самом `iptables` (эти настройки не переживают перезагрузку сами по себе), а в отдельном systemd-сервисе `firewall-openflux`, который применяет его заново при каждом старте сервера — поэтому после `sudo reboot` ничего вручную делать не нужно.

Проверить, что правило на месте:

```bash
openflux-ctl firewall
```

## Удаление всего

Убрать OpenFlux, оставив код и ключ на диске (на случай, если захочешь вернуться):

```bash
sudo openflux-ctl uninstall
```

Убрать вообще всё, включая ключ шифрования и скачанный код:

```bash
sudo openflux-ctl uninstall --purge
```

Оба варианта попросят подтверждение перед удалением.

## Устройство файлов (для любопытных)

```
/root/openflux/                    — код проекта (git) и собранная программа
/root/openflux-secrets/            — ключ шифрования и ссылки для каждой ноды
    encryption-key                 —   общий ключ (один на все ноды)
    <имя-ноды>.url                 —   ссылка конкретной ноды

/etc/systemd/system/openflux-*.service     — по одному файлу на каждую ноду
/etc/systemd/system/firewall-openflux.service — сетевое правило, применяется при загрузке

/usr/local/bin/openflux-ctl        — команда управления (эта используется каждый день)
/usr/local/bin/openflux-deploy     — скрипт обновления (вызывается автоматически)

/etc/cron.d/openflux-deploy        — расписание автообновления (появляется после `auto on`)
/var/log/openflux-deploy.log       — журнал всех обновлений
/root/openflux-checklist.txt       — последний отчёт команды `openflux-ctl check`
```

Всё это создаётся и обслуживается автоматически — руками туда лезть обычно не нужно, но если интересно посмотреть — теперь ты знаешь, что где лежит.
